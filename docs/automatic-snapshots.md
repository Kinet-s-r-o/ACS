# Automatic CPE snapshots

Edit/Add/Duplicate template → Snapshots configures two independent, disabled-by-default policies. Existing Provisioning Read/Write permissions cover these settings; no additional role grants are introduced. The effective template uses the existing manufacturer/product-class specificity and ID tie-breaker. Clone/import/export preserve the settings, while activating a new imported/cloned policy starts a new activation period.

Initial snapshot: a delay of 0–525600 whole minutes from the ONT's `devices.created_at`. Checks run at startup and every five minutes. Only ONTs added after that template's initial policy was enabled are eligible; enabling it does not backfill the existing fleet. Disabling and re-enabling starts a new activation period. The separate initial-delay policy records its successful completion once per ONT. Scheduled snapshots also ensure an initial snapshot exists, as described below.

Scheduled snapshots: 1–525600 whole minutes, checked at startup and every five minutes. Due slots are `PeriodicInformTime + N × interval`, from the cached `InternetGatewayDevice.ManagementServer.PeriodicInformTime` RFC3339 timestamp, including timezone and seconds. Missing/invalid/unknown (pre-1970) or future anchors do not produce snapshots. Slots predating ONT creation are ignored. Each scan handles the latest due slot, never a backlog; checks, shared queue throttling and CPE availability determine actual completion time.

Every ONT must have an initial snapshot. At completion of each scheduled refresh, the ACS checks for an actual snapshot with kind `initial` while holding the device row lock. If none exists, that scheduled snapshot is saved as a protected initial snapshot and both the initial and scheduled completion timestamps are updated in the same transaction. This includes older ONTs, devices with an outdated initial-completion marker after a Full operator deleted their initial snapshot, and templates with the separate initial-delay policy disabled. Later scheduled snapshots retain their normal kind. Existing manual/scheduled snapshots are preserved; only the next due scheduled snapshot supplies the missing initial snapshot.

Both policies enqueue an existing bulk summon system task with parameter refresh enabled, using the normal connection-request security and bulk limits. CWMP Off pauses scans and worker dispatch. A snapshot is saved only after its linked CPE refresh completes successfully. Failed contacts reuse their failed automation job on a later policy check. In-flight refreshes block duplicate jobs. Device-row locks serialize queue creation; snapshot creation, per-device completion markers and system-task completion are committed atomically. Restart recovery uses the existing system-task worker. Changing the effective template or disabling the policy prevents pending work from saving a snapshot.

Manual CPE snapshots also use the same Bulk Summon queue. POST `/device/{serial}/snapshots` now returns HTTP 202 with a pending system task, preserving the requested snapshot name and creator. The CPE UI follows that request and reports success only after both summon and the linked parameter refresh succeed; failed summon/refresh produces no snapshot. Manual requests do not depend on a provisioning template or automatic snapshot settings. CPE Write can create a request and track its own manual snapshot requests without System tasks access; it cannot inspect other operators' requests or unrelated bulk tasks. Restart during an unconfirmed manual contact fails that request without saving a snapshot; the existing retry action can queue it again. Empty writable parameter results fail the job without creating a snapshot.

All snapshots contain only confirmed writable parameters from the refreshed cache. Sensitive values remain encrypted at rest and use the existing snapshot read/restore permission checks. CPE Write can delete manual/scheduled snapshots; initial snapshots require CPE Full. The API enforces this independently of UI visibility. Retention cleanup excludes initial snapshots. Deleting an ONT retains the existing Delete CPE behavior for its owned records.

Storage adds `snapshots` JSONB and an initial-policy activation timestamp to templates, initial/scheduled completion timestamps to devices, kind/due-slot metadata to snapshots and automation metadata to system tasks. No new PostgreSQL indexes are introduced. The existing startup migration applies the added columns; the scheduler starts afterwards.

Backend: `models/snapshot_settings.go`, `database/snapshot_automation.go`, `snapshot_repository.go`, system-task completion and `cwmp/snapshot_scheduler.go`. UI: `components/TemplateSnapshotsForm.tsx`, `lib/snapshotSchedule.ts`, template modal in Provisioning and snapshot actions in DeviceDetail. Automatic jobs appear in System tasks → Bulk summon with creator `snapshot scheduler`; failures and retry attempts use the existing status/error display.

# Automatic CPE snapshots

Edit/Add/Duplicate template → Snapshots configures two independent, disabled-by-default policies. Existing Provisioning Read/Write permissions cover these settings; no additional role grants are introduced. The effective template uses the existing manufacturer/product-class specificity and ID tie-breaker. Clone/import/export preserve the settings.

Initial snapshot: a delay of 0–525600 whole minutes from the ONT's `devices.created_at`. Every accepted CPE Inform checks whether a saved snapshot with kind `initial` exists. If none exists, the initial policy is enabled and `now >= created_at + delay`, the ACS queues a Bulk Summon with parameter refresh. Zero permits a request on the first eligible Inform. This applies to older ONTs and to ONTs whose initial snapshot was deleted, regardless of activation dates or stale completion markers. Active snapshot jobs prevent duplicate requests; failed jobs retry on a later Inform.

Scheduled snapshots: an interval of 1–525600 whole minutes, checked on every accepted CPE Inform. The ACS reads the latest saved snapshot with kind `scheduled` and queues a Summon with parameter refresh when `now >= last_scheduled.created_at + interval`. If no Scheduled snapshot exists, the first interval starts at `devices.created_at`. Initial and Manual snapshots do not reset this timer; cached completion markers and PeriodicInformTime do not determine eligibility. Successful completion saves a Scheduled snapshot and records its completion time; failed attempts retry on a later Inform. A late Inform queues one request, without a backlog of missed intervals. There is no startup or periodic snapshot scan.

Initial (`initial`), Scheduled (`scheduled`) and Manual (`manual`) are independent snapshot types, shown in the snapshot list and detail. Each creation path preserves its type: a scheduled or manual snapshot never supplies a missing initial snapshot or changes the initial-completion marker. Missing initial snapshots are handled by the enabled Initial policy on Inform after its creation-time delay. Existing stored snapshots keep their recorded types.

All snapshot creation requires the persisted CPE Online flag. Inform handling marks the CPE Online before checking its policies; enqueueing rechecks that flag while locking the device. Offline devices create no summon/system task or snapshot and leave due markers unchanged; automatic checks retry on a later accepted Inform. Manual requests for Offline devices return HTTP 409 without creating a task. The worker rechecks status before creating a CWMP refresh or sending a connection request; a queued snapshot whose CPE is now Offline fails without sending summon. A final Online check before saving prevents snapshot creation if the CPE became Offline during the refresh. Existing non-snapshot summon/restart operations retain their behavior.

Both policies enqueue an existing bulk summon system task with parameter refresh enabled, using the normal connection-request security and bulk limits. CWMP Off pauses scans and worker dispatch. A snapshot is saved only after its linked CPE refresh completes successfully. Failed contacts reuse their failed automation job on a later policy check. In-flight refreshes block duplicate jobs. Device-row locks serialize queue creation; snapshot creation, per-device completion markers and system-task completion are committed atomically. Restart recovery uses the existing system-task worker. Changing the effective template or disabling the policy prevents pending work from saving a snapshot.

To clear an existing backlog, System tasks → Bulk Summon → Clear tasks offers status checkboxes. Select Pending to cancel queued work and any linked CWMP request that has not been sent; Processing, Waiting and already-sent CWMP work are protected. Existing System tasks Delete access is required. Disable the snapshot policies first if no new snapshot jobs should be queued; deleting pending jobs alone leaves those policies enabled. Saved snapshots are retained.

Manual CPE snapshots also use the same Bulk Summon queue. POST `/device/{serial}/snapshots` now returns HTTP 202 with a pending system task, preserving the requested snapshot name and creator. The CPE UI follows that request and reports success only after both summon and the linked parameter refresh succeed; failed summon/refresh produces no snapshot. Manual requests do not depend on a provisioning template or automatic snapshot settings. CPE Write can create a request and track its own manual snapshot requests without System tasks access; it cannot inspect other operators' requests or unrelated bulk tasks. Restart during an unconfirmed manual contact fails that request without saving a snapshot; the existing retry action can queue it again. Empty writable parameter results fail the job without creating a snapshot.

All snapshots contain only confirmed writable parameters from the refreshed cache. A partial refresh updates readable CPE values but carries a completion warning; snapshot jobs reject that warning and save no snapshot or completion marker. Ordinary Summon jobs retain the warning and complete after processing the remaining parameters. Sensitive values remain encrypted at rest and use the existing snapshot read/restore permission checks. CPE Write can delete manual/scheduled snapshots; initial snapshots require CPE Full. The API enforces this independently of UI visibility. Retention cleanup excludes initial snapshots. Deleting an ONT retains the existing Delete CPE behavior for its owned records.

Storage adds `snapshots` JSONB and an initial-policy activation timestamp to templates, initial/scheduled completion timestamps to devices, kind/due-slot metadata to snapshots and automation metadata to system tasks. No new PostgreSQL indexes are introduced. The existing startup migration applies the added columns; the scheduler starts afterwards.

Backend: `models/snapshot_settings.go`, `database/snapshot_automation.go`, `snapshot_repository.go`, system-task completion and Inform handling in `cwmp/handler.go`. UI: `components/TemplateSnapshotsForm.tsx`, `lib/snapshotSchedule.ts`, template modal in Provisioning and snapshot actions in DeviceDetail. Automatic jobs appear in System tasks → Bulk summon with creator `snapshot scheduler`; failures and retry attempts use the existing status/error display.
